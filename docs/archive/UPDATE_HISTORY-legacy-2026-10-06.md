## 2026-09-30 v0.0.56 의미 있는 진전

바로 성과물이 나오지 않는 탐색·연구형 ONE THING을 단순 부분 완료로 낮추지 않도록 `progress` 상태를 추가했습니다. 완료는 오늘 정한 결과까지 해낸 경우, 진전은 결과까지 못 갔지만 검증한 사실·제거한 선택지·확인한 장애물·분명해진 다음 행동으로 불확실성을 줄인 경우, 부분 완료는 일부 진행했지만 만족할 만큼 나아가지 못한 경우, 미완료는 실질적인 진행이 없었던 경우입니다. 노력했다는 사실만으로 진전을 자동 판정하지 않습니다.

자연어 해석, 현재·과거 후기 선택, 자연어 수정, 관리자 현황, 카드와 잔디가 같은 상태를 사용합니다. 잔디는 완료와 진전을 진한 초록, pending과 부분 완료를 연두, 미완료를 회색으로 표시하며 카드와 DB에서는 완료와 진전을 별도로 보존합니다.

SHA `ac9dd82b2d6f0a1bd9f2599496d97f79fd702b89`에서 기능을 배포한 뒤 비공개 `admin-dev`에서 실제 목표와 `후기: 진전`을 입력했습니다. `progress` 저장과 의미 있는 진전 카드, 진한 초록 잔디를 확인했습니다. 이 과정에서 `후기: 후기: 진전` 중복을 발견해 SHA `10c8a6ae776e2bfd19a237c4675710e2b7b43c6f`로 헤더 제거를 수정·재배포했고, 최종 Worker version `234197e4-8b65-4e25-b7bf-7d8fdaf81908`에서 회고 본문만 저장·표시되는 것을 Slack Web과 DB에서 다시 확인했습니다.

### 같은 상태를 다시 남긴 회원 원문 스레드의 잔디 복구

윤수님의 2026년 9월 29일 완료 상태와 후기는 공통 후기 흐름에서 먼저 저장되어 공통 스레드에 잔디가 게시됐지만, 이후 본인 목표 스레드에 남긴 `완료`는 같은 상태라는 이유로 변경 없음 처리되어 해당 스레드의 잔디가 갱신되지 않았습니다. 상태 저장 멱등성과 게시 위치 멱등성을 분리해, 같은 상태를 다시 남겨도 새 회원 원문 스레드에는 현재 revision의 잔디 projection을 생성하도록 수정했습니다.

SHA `ea74d79`와 Worker version `3a42e6a3-8531-46fa-94fa-6b50fef4ce2e`를 배포한 뒤 원래 `완료` 답글의 parent thread로 복구 delivery를 만들었습니다. delivery `garden:v2:2026-09-29:r2:t10d48576c394:sfbaa125c`가 한 번 전송되어 완료 잔디 `1790702702.758189`가 게시됐고, 같은 스레드의 이전 미확인 카드는 이미지 없이 보존됐습니다. 공통 스레드의 기존 완료 잔디도 그대로 유지됨을 Slack API와 DB에서 확인했습니다.

## 2026-09-18 v0.0.55 welcome 발행본 구현

welcome 안내를 변경 가능한 Slack 원문에서 신규 회원 입장 때마다 복사하던 구조를 폐기했습니다. 관리자가 `v0.0.55`와 원본·편집 시각, OT1L 로고·daily scrum 이미지 순서, 예상 canonical hash를 명시적으로 발행하면 migration 026이 정제 본문과 원본 metadata를 하나의 최신 발행본으로 고정합니다. Slack 원문 편집만으로는 전달본이 바뀌지 않습니다. migration 028은 Worker의 최신 발행본 조회·가입 전달과 관리자의 발행·대상 복구를 서로 다른 DB 역할과 자격증명으로 분리하고 `PUBLIC` 함수 실행 권한을 회수합니다. 신규 회원 자동 안내는 DB 최신 발행본만 읽고, 전체 채널 알림은 일반 텍스트로 바꿉니다. 전달 식별자에 불변 content hash를 포함해 같은 회원·같은 hash는 멱등 처리하고 새 hash의 수정본은 한 번 더 전달할 수 있습니다. 가입 안내와 특정 회원 수정본은 OT1L 봇 토큰으로만 게시하고 Slack 응답의 봇 작성자와 message timestamp를 확인·저장합니다. 운영 발행과 지정 회원 수정본은 Slack Web에서 봇 작성자·본문·이미지 순서를 확인했습니다. 배포 뒤 실제 신규 회원의 자연스러운 입장 이벤트부터 최종 게시까지는 아직 관찰하지 않았습니다.

## 2026-09-18 회원 기준 일괄 수집 운영 안정화

daily-scrum의 완전한 Slack 회원 목록을 실행 시점마다 확인하고, 이탈·삭제·봇 계정을 제외한 목표·후기 대상자를 공개 채널의 일괄 메시지로 묶습니다. migration 027은 오래된 스냅샷을 무시하고 재입장에도 기존 기록·시각·opt-out을 보존하며, 공통 글과 개인 due 일괄 글을 독립된 lease·최대 세 번 재시도·정확한 history 대조로 관리합니다. 대상자가 많으면 100명과 Slack 본문 한도 안에서 결정적으로 나눕니다. 10시·18시는 공통 현재 회원 수집이고, 11시·20시는 개인 기본값일 뿐 저장된 시각과 opt-out이 우선합니다. 토요일은 10시 선택 참여 글 한 번만 멘션 없이 보내고 일요일은 보내지 않습니다. 비공개 관리 채널의 수집 테스트와 현재 회원 일괄 게시를 Slack Web에서 확인했지만, 2026-09-19 주말 자연 실행과 2026-09-21 월요일 자연 실행은 아직 관찰 전입니다.

## 2026-09-29 정시 스크럼 단일 실행권과 당일 복구

Cron과 Durable Object가 동시에 정시 스크럼을 실행해 Slack 회원 API 호출이 겹치고, dispatch 생성 전에 둘 다 실패할 수 있던 구조를 제거했습니다. Cron만 공통 스크럼과 개인 재촉을 생성하며 Durable Object는 durable queue 유지보수만 담당합니다. 게시 본문은 DB 회원 snapshot으로 먼저 만들고 Slack 회원 동기화는 게시 뒤 별도 처리합니다. 목표는 후기 시각 전까지, 후기는 22시 전까지 같은 멱등 키로 복구합니다. `community-schedule-recovery`는 10시 17분에도 누락된 당일 글이 한 번 게시되고 Slack 프로필 조회가 선행 조건이 아님을 검증합니다.

2026년 9월 30일에는 10시용 5분 Cron 호출 자체가 실행되지 않아 첫 dispatch가 10시 5분에 만들어진 사실을 DB의 `reminder_first_attempt_at`으로 확인했습니다. 스케줄 실행권은 Cron 하나로 유지하되 오전 10시와 오후 6시의 독립된 정시 표현을 추가하고, 기존 5분 표현은 복구용으로 유지했습니다. 동시에 실행돼도 날짜·종류별 dispatch와 lease가 Slack 게시를 한 번으로 제한합니다.

2026년 10월 2일에는 Slack이 첫 목표 글을 수락했지만 Worker가 DB 영수증을 남기기 전에 끊겨 5분 복구가 같은 본문을 다시 게시한 사례를 확인했습니다. migration 065는 Slack message timestamp, dispatch 완료, prompt, 공통 thread 기준점을 원자적으로 저장합니다. 이전 lease가 Slack에 도달했는지 불확실한 재시도는 기존 글을 확인하지 못해도 자동 재게시하지 않습니다. 같은 배포에서 townhall 이벤트 진입을 추가했고, migration 066에서 활동·장소·최대 8개 시간 후보, 참여자의 복수 가능시간 선택, 주최자 수정과 동일 후보 응답 보존을 구현했습니다. 주최자는 버튼을 누른 Slack 계정으로 표시하고, 글의 스레드에서 참여 의견과 다음 이벤트 수요를 함께 받습니다.

같은 날 다운로드한 포켓몬 이미지 44개를 원본 보존·해시 중복 제거·이름 충돌 처리 뒤 Slack에 등록했습니다. Townhall 공지는 이름 목록 없이 짧게 유지하고 새 이모지 리액션은 공지 최상위 글에만 둡니다. 추가 수요를 받는 스레드 댓글에는 봇 리액션을 달지 않는 절차를 `docs/EMOJI_OPERATIONS.md`에 고정했습니다.

welcome 사용설명서 v0.0.62에는 Townhall의 `이벤트 열기`, 공통 장소, 최대 8개 시간 후보, 참여자의 복수 가능시간 선택, 주최자 수정과 스레드 수요 수집 방법을 추가했습니다.

후속 v0.0.65 운영 보정에서는 위 8개 후보 입력을 첫 Slack 모달에서 제거했습니다. 이제 활동·장소만 먼저 게시하고, 모든 새 이벤트 카드에 항상 보이는 `가능 시간 선택`에서 최대 14일 웹 시간표와 성사 조건을 설정합니다. 합성 QA도 기존 8개 입력을 기대하지 않고 실제 모달에 해당 문구와 입력 블록이 없으며 웹 시간표 버튼이 존재하는지를 검사합니다.

같은 날 `BUG-9C5FB6A973AFFCEC4914`의 자동 수정은 Codex 결과가 평일 회복 QA 기대값 하나를 빠뜨려 전체 검사에서 실패했고, 실행기가 같은 task receipt를 세 번 재사용한 뒤 reproduce 전용 실패 함수만 호출해 `fixing`에 멈췄습니다. migration 063은 실패한 fix 임대를 즉시 반납하고 새 Codex 작업으로 재시도하며 마지막 실패를 `fix_failed`와 Slack 알림으로 끝냅니다. migration 064는 자동 경로 소진 뒤 운영자가 main 병합·배포·검증한 근거를 갖춘 경우에만 완료 알림과 함께 `resolved`로 복구합니다.

### 2026-09-18 브라우저 QA 후속 보정

`후기:`·`회고:` 머리말은 저장 본문에서 제거하고, 본문의 숫자·시간·버전·`어제보다` 표현을 날짜 지시로 오인하지 않도록 선두 날짜 문법만 사용합니다. 이미 같은 결과가 적용된 `부분완료` 등의 재입력은 pending 확인만 닫고 이벤트·반응·잔디 카드를 추가로 만들지 않습니다. 합성된 서명 Slack 이벤트와 전체 검사로 고정했으며 운영 배포 전입니다.

## 2026-09-21 미출시 즉시 Slack 참여 정책 변경

v0.0.68은 운영자 검토 신청에서 확인된 회원 링크 기반 즉시 참여로 바꿉니다. 웹에서는 이메일 동의만 받고 이름과 자기소개는 Slack 가입 뒤 기존 모달에서 받습니다. migration 042는 `shared_invite` 예약을 lifetime 기본 한도 2명 안에서 원자적으로 만들며 R2 비공개 payload, 관리자 검토, 수동 초대 표식을 만들지 않습니다. v0.0.69는 실제 `team_join`의 Slack 계정 이메일이 예약 digest와 정확히 일치할 때만 출처를 기록하고 자기소개 버튼을 한 번 안내합니다.
