# 함께 만드는 흐름

현재 사용자 흐름의 기준은 이 문서입니다. 과거 Linear·버그 질문 절차보다 이 계약을 우선합니다.

## Slack에서 참여하기

`피드백·작업 제안`에 의견 한 줄을 남기면 접수됩니다. 원하는 변화는 선택 사항입니다. 빈 선택란 때문에 질문 세 번에 답하거나 접수가 만료될 필요가 없습니다. 일반 의견은 먼저 `의견 모으는 중` 작업 카드가 됩니다. 구현 가능한 현재 상황과 원하는 결과를 함께 적으면 AI 수정·검증 흐름으로 이어집니다. 취향·시안 검토·사용자 의견 모집을 무조건 코드 수정으로 처리하지 않습니다.

일반 feedback에서 시작한 의견은 원문을 보존하고 PO 작업으로 전달합니다. PO에서 시작한 의견, 질문, 실패, 재시도는 공개 feedback으로 돌아가지 않습니다. 일일 안내는 진입점이고 각 요청은 별도 작업 스레드를 가집니다.

담당 PO는 Slack에서 선택합니다. 활성 PO가 제안하면 본인이 기본 담당자이며 다른 PO에게 넘길 수 있습니다. Linear 가입이나 외부 계정은 필요 없습니다. 오래된 Linear 버튼은 안내만 하고 외부 상태를 바꾸지 않습니다.

## 직접 개발하거나 AI 도구로 작업하기

1. 자신의 GitHub fork를 로컬에 clone하고 `CONTRIBUTING.md`를 읽습니다.
2. 새 브랜치에서 수정하고 `bun install --frozen-lockfile`, `bun run check`를 실행합니다. DB 흐름을 바꾸면 임시 PostgreSQL 검사도 실행합니다.
3. 자신의 fork에 push하고 `Betalgeuse/ot1l:main`을 대상으로 PR을 엽니다.
4. Slack 작업 카드에서 **PR 연결하기**를 누르면 그 작업이 자동 선택됩니다. 가이드 버튼에서는 PR URL만으로 작업을 만들 수 있습니다. BUG 키를 외워 입력하지 않습니다.
5. 일반 PR은 격리 검사를 통과한 뒤 같은 스레드에서 정확한 SHA를 승인합니다. Open은 활성 PO/Founder, Core는 Founder가 승인합니다. 운영 키나 SSH 접근은 필요 없습니다.

자신의 바이브코딩 AI에는 다음과 같이 요청할 수 있습니다.

> 이 저장소의 AGENTS.md와 CONTRIBUTING.md를 먼저 읽어줘. 요청한 변경의 소유 Worker와 승인 경계를 확인하고, 내 fork의 새 브랜치에서 구현·검사한 뒤 PR 링크를 알려줘. 운영 비밀을 요청하거나 로컬에서 배포하지 마. 시안 검토 단계이면 Draft로 남겨줘.

## 시안과 사용자 의견

Draft PR은 **시안 검토 중**으로 연결하며 병합 큐에 넣지 않습니다. 기존 화면과 미리보기를 함께 보고 같은 Slack 작업 스레드에 의견을 남깁니다. 검토한 commit SHA를 기록해 미리보기 변경 전후의 의견을 구분합니다. 의견 수집과 실제 기능 반영은 다른 단계입니다. 작성자가 Draft를 해제한 뒤 다시 검증을 요청해야 승인 단계로 진행합니다.

`design-preview/**`는 운영 Worker 배포 경로가 아닙니다. 독립된 미리보기를 보존하며, 실제 홈페이지 적용 PR은 `site/**` 변경 범위와 가입·보안 영향까지 따로 검토합니다.

## PO 승인과 배포 화면 계약

| 사용자와 진입점 | 보이는 상태·버튼 | 클릭 결과 |
| --- | --- | --- |
| 일반 회원의 feedback | 원문과 PO 참여 진입점 | PO 활성화 전에는 병합 승인 불가 |
| 활성 PO의 `#po-work` 작업 스레드 | 실제 의견·단계·DRI 선택·PR 연결, Open 검증 완료 시 `Product Owner 병합·배포 승인` | 정확한 SHA·파일 목록·배포 대상 승인 후 Broker가 병합하고 모든 해당 Worker 반영 |
| Founder의 같은 스레드 | 보호 영역 검증 완료 시 `Founder 병합·배포 승인` | 보호 변경만 Founder 승인, 나머지는 PO와 동일한 배포 경로 |
| 승인 이후 같은 스레드 | 승인 버튼 제거, 반영 중, 최종 결과 | 문서·QA·시안은 저장소 반영 완료, Worker는 대상별 버전·health 확인 뒤 결과 통지 |

PO가 승인하면 별도 Founder 배포 버튼이나 운영 키 전달이 필요 없습니다. 홈페이지와 이벤트가 함께 쓰는 CSS는 두 Worker에 모두 반영합니다. 여러 Open 제품 영역을 섞어도 Founder 요청으로 바꾸지 않습니다. 가입/개인정보·권한·배포기 자체와 운영 능력을 가진 백엔드는 보호합니다. 파일 이름에 security라는 말이 있다는 이유만으로 일반 문서를 보호 변경으로 분류하지 않습니다.

승인 정책 변경은 기존 승인에 소급 적용하지 않습니다. 이전 digest로 대기 중인 요청은 재검증해서 새 승인 카드를 받아야 합니다. PO 자격은 본인이 활성화하며, 이 정책 변경으로 회원을 자동 승격하지 않습니다.

## 내부 소유권과 복구

- `community-bug-start.ts`: 의견 접수와 구체적인 AI 작업 요청의 분리. 과거 버그 상세 접수는 이력 호환용이며 일반 버튼의 기본 경로가 아닙니다.
- `community-maintainer-work.ts`, migration 089: Slack 작업 카드와 담당자. 기존 테이블 이름은 호환을 위해 보존하지만 Linear가 상태의 원본은 아닙니다.
- `community-pull-request.ts`, migration 090: 작업과 PR 연결. Draft 검토와 실행 요청 분리.
- migration 088: 승인된 `changeClass`, `changedPaths`, `classificationDigest`를 병합 실행기에 전달.
- `automation/runner/**`: 정확한 SHA, 파일 범위, 격리 검사, 승인, 병합과 배포. 재시도 시 이미 checkout된 SHA도 같은 승인 범위로 검증.
- `community-notification-thread.ts`: Slack 수신 기록과 스레드 존재 확인. 삭제된 원본에 새 최상위 글을 만들지 않음.

운영 완료는 merge나 health만으로 판정하지 않습니다. 실제 권한별 클릭과 상태 전환, 담당자·버튼 유지, 최종 결과 댓글을 확인합니다. 확인되지 않은 항목은 미검증으로 남깁니다.

실제 비밀키·개인정보 원문은 계속 보호합니다. 보안·secret이라는 단어만 언급한 일반 의견을 비공개 사건으로 분류하지 않습니다. 과거 암호화 원본·사람 댓글·검토 이력을 임의로 삭제하지 않습니다.
